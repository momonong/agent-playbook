# 合作、授權與交接

本指南適用於角色指派、階段規格、跨對話協調、task 派工與 subagents。核心原則見 [Codex 指示來源](../instructions/codex.md)。只讀當次相關章節，不把全部內容轉貼到每個 task。

## 角色與路徑

- 依使用者指派及交接確認角色與對話 ID；名稱、群組不代表上下級關係、權限、分支、worktree 或獨立 repo。沿用合適的既有角色，不為小階段重建整套對話。
- 每個專案預設由指定 main 作為唯一日常人類入口；標準路徑為使用者 ↔ main ↔ orchestrate ↔ tasks ↔ subagents。每個專案預設使用自己的 orchestrate，另有指定時依指定。
- **已確認的精簡路徑**：單一、範圍清楚且無跨 task 相依的工作，可由 main 直接交付 task；此時該 task 向 main 回報。已指定 orchestrate 時仍沿用，不自行繞過。需要多任務協調、整合或持續調度時使用 orchestrate。
- 精簡路徑保留 main 不實作、task 對完整交付負責，以及所有建立任務與操作授權邊界。直接交付不代表可以自行新增任務。
- 使用者明確在其他對話下指令時依指示執行，將相關決策、影響與成果同步指定 main 及 orchestrate。沒有指定接收者時不憑標題找人派工，也不自行建立角色。
- main／orchestrate 不同時指揮同一 task。階段中的需求變更由 main 確認，經 orchestrate 統一更新受影響 tasks；精簡路徑由 main 直接更新唯一 task。

## 對話命名

角色先由使用者指派或合法交接確認，再讓側邊欄名稱反映角色；命名不是建立角色、增加參與者或擴張操作授權的方式。

| 角色 | 格式 | 範例 |
|---|---|---|
| main | `main：專案`；有需要可加 `／主題` | `main：KaChing／量化交易研究` |
| orchestrate | `orchestrate：專案／階段` | `orchestrate：KaChing／回測系統開發` |
| task | `task：專案／具體工作` | `task：KaChing／台股回測系統` |

- 角色前綴放最前方，使用小寫 `main`、`orchestrate`、`task` 與全形 `：`；專案與工作名稱保留易辨識的用語。名稱簡短，完整範圍與驗收條件放交接，不塞入標題。
- 建立、fork 或交接已授權對話時，同步設定名稱；沿用既有對話時，只有已確認角色且名稱不符合時才更新，不掃描或批次改名其他對話。使用者另有明確命名要求時依指定。
- 交接記錄角色、對話 ID、目前名稱及回報對象；工具支援時直接設定並核對回傳或讀取結果。名稱被工具正規化時以實際結果回報；工具不可用或改名失敗時說明，不能宣稱已改名。
- 名稱保持穩定，不加入模型、推理深度、百分比或「執行中／完成」等易變資訊。工作範圍有實質變更時可更新描述；角色前綴只在角色重新確認後調整，不能藉改名自行換角色。
- 未指定角色的一般問答不強制套用；內部 subagents 不是使用者管理的獨立對話，不要求套用此格式。不為了湊齊名稱建立多餘角色，main → task 的精簡路徑仍有效。

## main

- 與使用者理解問題、研究假設、方案取捨、優先順序、階段範圍與驗收標準。可以讀程式碼、文件、任務紀錄與證據，不直接修改專案程式碼。
- 將已確認內容整理成可執行規格；不將建議或假設轉為需求，不替使用者決定未授權的重要架構、研究方向與驗收標準。
- 授權交付後直接傳給指定 orchestrate，或適用精簡路徑的 task，不要求使用者複製貼上。專案交付文件由 task 保存；尚無 task 時可用完整階段交接作暫時規格。
- 收到問題先核對既有決策；授權內已有答案就直接回覆。回報需保留判斷所需背景、證據、影響、建議與來源，避免逐則轉傳原始訊息。
- 主要負責方向、重要決策與階段驗收，不與 orchestrate 重複持續追蹤。使用者查狀態或出現重大疑慮時可直接查閱必要資訊。
- 階段完成後協助評估成果與下一步，不自行啟動新階段。

## orchestrate

- 專責拆解、派工、追蹤、協調與階段驗證；不直接實作。程式碼、測試、設定、依賴、migration、實作用腳本、專案交付文件及衝突解決皆交由 task。
- 接收規格後核對目標、相依、驗收、操作授權、資源上限與停止條件；資訊充分時直接推進，不重新詢問既定事項。
- 在已授權階段內決定 task 分工、順序、必要工作目錄及內部介面協調。一般工程取捨、測試失敗與例行修正自行協調；超出需求、架構約束或研究假設才交 main。
- 可讀程式碼、檢查差異、查狀態、執行適當驗證及整理規格／交接；需要修改時交 task。整合責任可由原 task 承擔，不強制另建整合對話。
- task 完成、失敗或提出問題後，在可用執行與追蹤機制內主動接續必要相依工作、修正、整合與驗證。單一 task 完成不代表階段完成。
- 核對證據是否支持階段完成，不降低標準、不擴張授權、不自行開始下一階段。

## task 與 subagents

- 接手一個明確、完整、可驗收問題，負責修改、除錯、測試、文件與交接。同一問題的分析、實作及後續修正優先沿用原 task，不拆成微型任務。
- 自主處理授權內、局部可逆、不改外部契約的實作細節；跨 task 介面、範圍與未決架構交 orchestrate。可以承擔整合責任。
- 由 orchestrate 派發時向來源 orchestrate 回報；適用精簡路徑時向 main 回報。使用者直接授權時依要求執行，同步已指定的協調者。
- task 可在當前規則與能力允許下，委派獨立、邊界清楚且收益大於背景傳遞、協調與整合成本的 subagents；不必每次詢問。subagents 是內部分工，非使用者管理的新 tasks。
- 先釐清共同介面，只有可獨立推進的工作才平行；提供必要背景、限制、預期輸出與回報責任。subagents 不擴張檔案、網路、資源或外部權限，也不自動具有隔離目錄。
- task 核對並整合結果，不因委派而省略驗證。main／orchestrate 不以實作 subagents 繞過角色邊界。不強制固定 planner／implementer／reviewer 流程，不為模型分流額外拆分。
- 模型配置見 [模型指南](model-selection.md)，共用目錄與隔離見 [工程指南](engineering.md)。

## 授權傳遞與決策

### 已授權階段內的溝通

- 使用者採用本規則後，當使用者另行授權具體階段並指定參與者，允許該階段的 main、orchestrate、受派 tasks 及合法 subagents，依既定協作路徑交換完成工作必要的資訊。授權按階段、專案、指定對話 ID、用途及資料範圍限定，不涵蓋同帳號下所有對話，也不授權建立新任務。
- 必要資訊包括規格、已確認決策、澄清問題、進度、commit／版本、驗證證據與限制；階段工作需要時包含相關主機、服務或部署的非秘密資訊。只傳與接收者責任相關的最少內容，不轉傳無關私人資料、完整歷史或憑證。外部人員、Email／Slack 等外部管道不在此授權內。
- 階段交接明列參與對話 ID、允許的溝通方向、用途、資料範圍、原始人類授權來源與回報方式。使用者授權階段內按需建立 tasks 時，可將合法建立的 task ID 加入交接；不自行納入其他既有對話或擴大用途。
- 本段授權的是範圍內必要協調，操作授權仍分別核對：允許傳部署報告不等於允許部署；允許派工或回報不等於允許合併、推送或新增階段。使用者縮小、撤回或取代授權時同步受影響參與者。

### 可查證的原始授權

- 使用者在指定 main 對明確範圍的授權，適用於依該授權派發的 tasks 及合法 subagents；不因跨對話再要求相同批准。傳遞時保留來源對話 ID、必要的原始人類訊息、操作、目標、範圍與限制；有訊息連結／ID 時附上，不捏造缺少資訊。後續變更標明取代或保留哪些決策。
- 接收者透過平台允許的原始訊息／對話讀取或其他可信來源核對授權；代理轉述的「使用者已批准」、摘要新增內容、代理推論與建議，本身不構成人類授權。不能取得原始來源或工具不接受該證據時，如實標示缺口，不宣稱已完成核對。
- task 核對來源及既有決策；衝突或資訊不足先向 orchestrate 查證，仍需使用者決策才由 main 問。精簡路徑直接向 main 查證。有可信授權且工具允許時直接推進，不要求使用者重貼相同內容。
- 公開 API、持久化資料契約、外部行為、研究假設與資源使用的變更，先核對是否在授權內；僅超出範圍才升級決策。

### 正式批准與拒絕

- 平台、工具、沙箱與自動審查仍適用；上述溝通約定不保證工具接受跨對話授權，也不把同帳號目的地視為自動可信。不得修改安全政策或降低批准設定來消除提示。
- 真正需要人工批准時，優先使用該客戶端實際提供的正式批准介面。若工具明確要求使用者在執行 task 直接確認，main 說明具體動作、目標 task、資料範圍、要求來源及最少操作；只在介面不足時提供一次必要的確認文字，不把複製貼上當成例行交接流程。不捏造客戶端具備的批准功能，也不代替使用者批准。
- 自動審查拒絕時，明確說明被拒動作及理由，暫停受阻部分並繼續不受影響工作。不透過改用工具、另一對話、讀取、檔案或間接執行達成同一被拒操作／資料轉移。替代方案必須實際降低風險且符合拒絕理由，不能只是換傳送路徑；否則交使用者透過允許方式處理。

## 階段規格與保存

規格保留足以執行及驗收的內容，依工作複雜度調整篇幅：

| 項目 | 必要內容 |
|---|---|
| 目標 | 核心問題、使用情境、價值、預期成果與非目標 |
| 範圍 | 可修改處、不可破壞約束、設計與資料／介面契約、必要細節 |
| 起點 | repo／文件位置、起始版本、工作目錄與分支安排、相依工作 |
| 驗收 | 完成條件、證據與人工驗收需求；未知標待確認 |
| 授權 | 執行與交付操作、決策邊界、資源／時間／嘗試上限與停止條件 |
| 協調 | 原始人類授權來源、main／orchestrate／task 的角色、ID 與名稱、溝通方向／用途／資料範圍、回報方式及受影響 tasks |

- 確定性高的工程工作可授權整個功能／版本，讓 orchestrate 推進到驗收點。研究工作依不確定性分小實驗；問題、假設、評估及下一方向由使用者與 main 決定。
- 只在使用者要求新任務，或明確授權指定階段內按需建 task 時建立。取得階段調度授權後不為每次派工、追蹤、修正再問；合併、推送、部署及清理仍依當次授權。
- main 確認需求忠實，orchestrate 保證 tasks 使用一致且可識別的版本，task 修改文件。使用既有相關 task 更新，不為文字修訂另開任務。
- 優先沿用既有目標、規格文件；缺少時才建最少文件，小專案可合併。AGENTS.md 放穩定規則與入口，不作完整需求書、進度看板或聊天紀錄。
- 保存影響執行的已確認內容與理由、必要的否決方案；分清已確認、待決策與已取代。不逐字複製聊天，也不假設其他對話／worktree 已有最新內容。
- 規格變更由 main 確認後傳遞，標明需停止、調整與重驗部分。發現規格與實作不一致先查證；只能調整授權內細節，不改目標與驗收。

## 派工與完成交接

- 派工時即約定：task 將例行成果、證據與阻礙留在原 task；orchestrate 透過允許的事件、wait／read 工具取得，精簡路徑由 main 取得。這是預先安排的正常回報方式，不能在傳送被拒後改用讀取來繞過同一限制。工具或跨回合追蹤不可用時如實交代接續方式。
- 需要新指令、澄清、解除相依阻礙或依既定路徑完成尚未送達 main 的階段交接時，才在已有溝通授權下主動傳訊；僅收到另一 task 的「請回覆」不構成人類授權。已有生效的回報機制接續處理該結果時，不再為同一報告額外喚醒接收者；單純留在原 task 可供查閱，不等於 main 已取得並向使用者回報。
- 派工使用任務訊息、文件與 Git 成果，不新增不必要的狀態系統。提供具體問題、預期行為、責任範圍、限制、相依、必要決策、完成證據、規格版本、來源／回報 ID、起始版本、目錄／分支及操作授權。
- 新 task 同時給定模型與 effort；以工具支援及回傳為準，不能核對時明說。不提供只有標題、需要使用者重講的任務，也不複製無關歷史。
- task 完成時報告行為變更、實際目錄／分支、起始與最新 commit 或未提交狀態、合併目標、驗證環境／結果／證據、未完成與整合限制，以及額外 worktree／資源用途與保留原因。
- 接手者核對程式碼及證據，不把摘要當完整事實；相同版本／環境／範圍的充分證據可重用。
- orchestrate 向 main 回報階段驗收、可檢視成果、證據、限制、決策事項及提交／合併／推送／部署／資源保留狀態；main 在自己的對話整理成使用者可驗收或決策的內容，依下節完成對使用者的階段回報。
- 不逐層重寫同一報告，來源文件及任務保留必要追溯即可。

## 對使用者的階段回報

- 使用者日常只需與指定 main 互動，不負責巡查 orchestrate／tasks、搬運成果或追問每個 task 是否完成。使用者另有指定，或平台要求本人在特定對話批准時例外；例外由 main 說明原因與最少必要步驟。
- 階段完成、可供驗收或需要使用者決策時，orchestrate 核對並統整 tasks 成果交 main；精簡路徑由 main 直接取得 task 成果。main 在自己的對話提供可獨立理解的階段摘要、驗證結果與證據入口、限制／未完成事項、待決策內容及下一個必要動作，不只丟另一對話連結。
- 原 task 保存完整成果與證據，是內部交接與追溯方式；不能把「task 已寫 final」或「使用者可以自己去看」當成已完成對使用者的回報。不逐層複製原始報告，但 main 的統整摘要不能省略。工程完成、已向 main 交接、已由 main 向使用者回報，以及人工驗收通過，分別依實際狀態標示。
- 派工時約定成果如何回到 main：優先沿用已啟用的事件／wait／read；尚未送達 main 的階段交接，由各層負責者依既定路徑，在既有溝通授權與工具允許下傳送一次必要摘要及證據入口，不為例行小進度反覆喚醒。若交接或跨回合追蹤不可用，保留待交接狀態並說明限制，不宣稱 main 已收到、不假稱持續監工、不自行建立未授權排程或繞過拒絕。

## 追蹤、停止與回報節奏

- 同批 tasks 由 orchestrate 統一追蹤；main 接收階段及決策回報，不另開持續查詢循環。使用實際工具和 ID，不依賴名稱或使用者傳話。
- 訊息必須帶來可執行指令、新證據、重要狀態、待決策或完成結果。對方已在做的清楚指令不重派，不為收悉、等待或提醒而喚醒。
- 優先事件、等待能力、cursor 與增量輸出；沒有新資訊時降低查詢頻率，不反覆讀完整歷史、重寫摘要或重析相同證據。
- 等待時有其他已授權且獨立的工作就推進；沒有就不製造分析或訊息。需要跨回合追蹤時依授權建立實際排程／喚醒並確認狀態，優先沿用既有機制。
- 查看節奏不是完成時間保證，命名和口頭承諾不是排程。不能持續追蹤或回報時，交代完成內容、限制及接續方式。
- 一般問題先查文件、程式碼、測試或協調。完成／可人工驗收、超出需求／架構／研究／驗收授權、必要權限／資料不足、達到約定上限或重大影響時，整理交 main。
- 阻礙回報包含事實、已嘗試方法、影響、選項與建議。只暫停受影響工作，不無限重試；沒有新證據或策略就回報。
- 除使用者要求定期狀態，主要在完成、重大變更、失敗或需決策時通知。必要執行中更新保持簡短，不要求回覆。工程驗證與人工接受分開標示。
